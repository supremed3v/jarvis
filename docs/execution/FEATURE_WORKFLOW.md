# JARVIS Feature Workflow

## Document Type

Execution / Process Documentation

## Purpose

Describe how a JARVIS feature moves from specification to completion, and
which component is responsible for each step. This is the engineering
automation layer around the spec library — it does not implement any JARVIS
product feature itself.

---

# Lifecycle

```
Feature Discovery
        |
/feature load
        |
context/current-feature.md
        |
/feature start
        |
Implementation
        |
/feature test
        |
/feature review
        |
/feature explain
        |
/feature complete
```

1. **Feature Discovery** — a human or agent decides which SPEC to work on
   next, guided by `context/features/FEATURE_INDEX.md` and
   `docs/execution/JARVIS_IMPLEMENTATION_ORDER.md` (never jump ahead of the
   phase order).
2. **`/feature load <spec-name>`** — routes through the Feature Index first,
   reads the target SPEC, resolves dependencies, and writes
   `context/current-feature.md` with the active working state. See
   `.claude/skills/jarvis-feature/actions/load.md`.
3. **`context/current-feature.md`** — the single source of truth for "what
   are we working on right now." Every later step reads this file instead
   of re-deriving state.
4. **`/feature start`** — begins implementation of the loaded feature
   (`.claude/skills/jarvis-feature/actions/start.md`).
5. **Implementation** — actual code changes, scoped to the loaded SPEC only.
6. **`/feature test`** — runs/validates the feature's testing criteria
   (`.claude/skills/jarvis-feature/actions/test.md`).
7. **`/feature review`** — reviews the change against
   `docs/agents/CODE_REVIEW_PROTOCOL.md`
   (`.claude/skills/jarvis-feature/actions/review.md`).
8. **`/feature explain`** — produces a human-readable explanation of the
   change (`.claude/skills/jarvis-feature/actions/explain.md`).
9. **`/feature complete`** — closes out the feature: updates status tracking
   (e.g. `docs/agents/JARVIS_BUILD_TRACKER.md`) and clears/rolls over
   `context/current-feature.md`
   (`.claude/skills/jarvis-feature/actions/complete.md`).

# Component Responsibilities

## `context/features/FEATURE_INDEX.md`

Auto-generated navigation layer over all `SPEC-NNNN-*.md` files. Currently
generated by `scripts/generate_feature_index.ps1` and contains, per spec:
`SPEC-ID`, feature name, `File`, and `Status`. It is the **first** file read
by the load workflow — agents locate a spec here before opening it, so they
don't have to scan the full spec library.

It does not yet carry explicit `Dependencies:` / `Related:` blocks per
entry, even though `FEATURE_INDEX_SPEC.md` describes that as the target
design. The tooling in this workflow (`load.md`, `check_dependencies.ps1`,
`setup_feature.ps1`) is written to use those fields when present and fall
back to `JARVIS_IMPLEMENTATION_ORDER.md` / `JARVIS_DEPENDENCY_GRAPH.md` /
the spec's own Requirements text when absent — see
"Known Gaps" below.

## `context/features/FEATURE_INDEX_SPEC.md`

The design specification for the index itself: what fields an entry should
have, how specs are categorized into layers, and the agent usage rules for
consulting it before individual specs. Read this to understand *why* the
index is structured the way it is, not to find feature data.

## `context/current-feature.md`

The active-state file for whichever feature is currently loaded. Reset to
the blank template (`Working In: Not Started`, `Status: Not Started`, empty
`Goals`/`Dependencies`/`Notes`/`History`) when no feature is active, and
regenerated by `/feature load` or `scripts/setup_feature.ps1` when one is.
Every other workflow action (`start`, `test`, `review`, `explain`,
`complete`) reads this file rather than re-resolving the spec/dependency
chain itself.

## Claude feature skill (`.claude/skills/jarvis-feature/`)

The `/feature <action>` command surface. `SKILL.md` lists the available
actions; each `actions/*.md` file defines the step-by-step procedure an
agent follows for that action. `load.md` is the entry point that makes
`FEATURE_INDEX.md` the routing layer, per
`context/features/JARVIS_FEATURE_INDEX_INTEGRATION_SPEC.md`.

## `scripts/`

Command-line automation supporting the workflow, all run from inside
`scripts/` (relative `../` paths):

| Script | Responsibility |
|---|---|
| `rename_specs.ps1` | Normalizes SPEC filenames to `SPEC-NNNN-kebab-case-title.md`. |
| `generate_feature_index.ps1` | Regenerates `FEATURE_INDEX.md` from all `SPEC-*.md` files. |
| `validate_specs.ps1` | Checks filename format, required sections (`# Title`, `## Purpose`, `## Requirements`, `## Acceptance Criteria`), and duplicate SPEC IDs. |
| `check_dependencies.ps1` | Confirms every `Dependencies:` reference in `FEATURE_INDEX.md` points at a SPEC file that actually exists. |
| `validate_structure.ps1` | Confirms the repository skeleton (`context/features/`, `docs/execution/`, `apps/`, `services/`, `agents/`, `packages/`, `tests/`, etc.) is present. |
| `setup_feature.ps1 <spec-name>` | Scripted equivalent of `/feature load`: reads the index, validates dependencies, reads the SPEC, and regenerates `context/current-feature.md`. |
| `_lib_feature_index.ps1` | Shared parsing functions (`Get-FeatureIndexEntries`, `Find-FeatureIndexEntry`, `Test-SpecFileExists`) dot-sourced by `check_dependencies.ps1` and `setup_feature.ps1` so both use identical extraction logic. Not run directly. |

# Known Gaps

- `FEATURE_INDEX.md` entries do not currently declare `Dependencies:` or
  `Related:` blocks, so `check_dependencies.ps1` and `setup_feature.ps1`
  will report 0 dependencies checked until either
  `generate_feature_index.ps1` is extended to emit them, or they are added
  by hand per `FEATURE_INDEX_SPEC.md`'s Maintenance Rules. Populating that
  data for all 182 specs was explicitly out of scope for this workflow-only
  pass — see `context/features/JARVIS_FEATURE_INDEX_INTEGRATION_SPEC.md`
  history in `context/current-feature.md`'s prior notes.
- `generate_feature_index.ps1`'s here-string has a pre-existing PowerShell
  backtick-escaping quirk that collapses its intended triple-backtick code
  fences to single backticks, and an encoding issue that mangles the em
  dash (`—`) in section headers to `â€”`. `validate_specs.ps1` and
  `_lib_feature_index.ps1` are written to tolerate this, but the generator
  itself was not modified (out of scope — no spec/architecture files were
  to be touched, and fixing the generator wasn't one of the requested
  tasks).
- Running `validate_specs.ps1` against the current spec library will report
  most/all specs as `INVALID` because existing specs use `## Overview` /
  `## Testing` headings rather than the `## Purpose` / `## Acceptance
  Criteria` headings this workflow now requires. This is expected — the
  validator is new tooling surfacing a real gap, not a sign specs were
  edited.
